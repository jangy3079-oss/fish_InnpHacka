# SRS — 조피볼락 상태 진단 멀티센서 AI 가두리 관리 플랫폼

Nov 27, 2026 · @해리

## 1. 개요

이 문서는 경남 남해안 해상가두리 조피볼락의 행동을 소나·카메라로 측정해 스트레스 지수를 만들고, 원인을 추정해 대응과 손익을 추천하는 시스템의 요구사항을 정의한다. 기준은 최종 기획안(2026-11-27)이며, 1단계(해커톤 MVP)와 2단계 이후(현장 실증)를 구분해 적는다.

### 1.1 목적

- 해역 수온이 아닌 **물고기 상태**를 상시 측정한다.
- 이상 신호의 **원인을 '의심' 수준으로 추정**한다 (고수온 피신, 피난처 소실, 저산소, 적조, 질병 의심, 기생충 의심, 작업 스트레스, 섭식 저하).
- 원인별 **대응 선택지와 손익을 비교**해 어민의 결정을 돕는다. 최종 결정은 어민이 한다.
- 지자체에 **해역별 스트레스 지도**를 제공한다.

### 1.2 범위

| 구분 | 포함 | 제외 |
| --- | --- | --- |
| 대상 어종 | 조피볼락 (Sebastes schlegelii) | 다른 어종 (4단계 확장) |
| 대상 시설 | 경남 해상가두리, 해역 대표 가두리(센티넬) | 육상 양식장 (4단계 확장) |
| 기능 | 측정, 상태 진단(스트레스 지수, 질병·기생충 의심 신호 포함), 원인 추정, 대응·손익 비교, 알림, 대시보드 | 병명 확정·약품 처방(수산질병관리사에게 연결), 장비 원격 제어 |
| 해커톤 | 합성 소나, 공개 영상, 규칙 기반 원인 추정 | 실측 폐사 예측 모델(M7) |

### 1.3 용어 정의

| 용어 | 정의 |
| --- | --- |
| 센티넬 가두리 | 해역을 대표해 센서를 설치하는 가두리. 같은 해역 어가에 경보를 공유한다 |
| 스트레스 지수 | 가두리별·밤낮별 평소 기준선 대비 행동 이탈 정도 (0\~100) |
| 경보 단계 | 정상 / 주의 / 경고 / 위험 4단계 |
| 수직 분포 | 수심 구간별 어군 비율 (저층·중층·표층 쏠림) |
| 피난처 소실 | 층간 수온 차가 사라져 중층으로 피신할 곳이 없어진 상태 |
| 에코그램 | 소나가 수신한 음향 신호를 시간×수심으로 나타낸 영상 |
| 영상 품질 점수 | 프레임의 대비·선명도·밝기로 계산한 신뢰도 (0\~1) |
| 의심 원인 | 행동 패턴과 환경 신호로 추정한 원인과 그 확률·근거 |
| 몸 비비기 | 개체가 그물·바닥에 몸을 문지르는 행동. 외부 기생충이나 아가미 자극 때 늘 수 있어 '기생충 의심' 신호로 쓴다 |
| 공통 1차 조치 | 질병·기생충 의심 때 약품 없이 하는 관리 조치 (수과원 공식 자료에 근거가 있는 사료 공급 조절, 밀도 조절, 폐사체 즉시 수거. 작업 도구 소독과 산소 보강은 질병 상황의 근거가 확인될 때까지 보류) |

## 2. 전체 설명

이 시스템은 기존 해역 수온 특보 체계 위에 **물고기 상태 층**을 더하는 독립 서비스다. 수온 데이터는 국립수산과학원 자료를 가져오고, 행동 측정·원인 추정·대응 추천은 이 시스템이 맡는다.

### 2.1 제품 관점

- 현장 장비(소나, 카메라, 층별 수온·DO 센서) → 엣지 장치 → 서버 → 어민 앱·지자체 대시보드 순서로 데이터가 흐른다.
- 기존 플랫폼(수과원 실시간 해양환경 어장정보시스템, 완도 AI 수산양식 플랫폼)과는 대체가 아니라 연동 관계다.
- **바로 쓸 수 있는 오픈소스는 직접 만들지 않고 가져다 쓴다.** 목록과 라이선스는 5.3절에 있다.

### 2.2 사용자 유형

| 사용자 | 주요 목적 | 주 화면 | 기술 수준 |
| --- | --- | --- | --- |
| 양식 어민 | 내 가두리 상태와 할 일 확인 | 모바일 알림, 간단한 상태 화면 | 낮음, 고령층 다수 |
| 시·군·도 수산 공무원 | 해역별 위험 파악, 방류 수요 예측 | 웹 대시보드 | 보통 |
| 수산질병관리사 | 질병 의심 신호 확인, 진단 요청 접수 | 진단 요청 목록 | 전문가 |
| 수협·재해보험 | 피해 이력, 시세 연동 | 리포트 (2단계 이후) | 보통 |
| 시스템 관리자 | 센서·모델·규칙 관리 | 관리자 콘솔 | 높음 |

### 2.3 운영 환경

- **현장:** 경남 남해안 해상가두리. 태양광과 배터리 전력, LTE 통신, 염분·태풍에 노출된다.
- **엣지:** Jetson 계열 장치에서 영상·소나를 현장 처리하고, 서버에는 지표만 보낸다.
- **서버:** Python 백엔드, PostgreSQL(Supabase).
- **클라이언트:** 어민은 모바일 알림과 모바일 웹, 지자체는 PC 웹 브라우저.
- **해커톤:** 현장 장비 없이 합성 데이터와 공개 영상으로 노트북·클라우드에서 실행한다.

### 2.4 제약 사항

| ID | 제약 |
| --- | --- |
| C-01 | 시스템은 질병·기생충을 '의심' 수준까지만 추정한다. 병명을 확정하거나 약품(항생·항균제, 백신 등)을 처방하지 않으며, 약품명·투약량도 안내하지 않는다. 진단과 처방은 수산질병관리사에게 연결한다 |
| C-02 | 방류·출하 같은 재산 결정은 추천만 하고 최종 결정은 어민이 한다 |

| C-04 | 알림의 대응 요령은 국립수산과학원 공식 관리요령만 근거로 한다 |
| C-05 | 살아 있는 물고기에게 스트레스를 주는 실험은 하지 않는다 |
| C-06 | 상용화 단계에서는 AGPL 라이선스 컴포넌트(Ultralytics YOLO, Community Fish Detector)를 허용 라이선스 대안으로 바꾸거나 상용 라이선스를 확보한다 |
| C-07 | 해커톤 마감은 2026-11-28 12:00이며, 이 범위를 넘는 기능은 확장 기능으로 둔다 |

## 3. 기능 요구사항

기능 요구사항은 7개 영역 45개다. 우선순위 **M**(필수)은 해커톤 MVP에 들어가고, **S**(권장)는 시간이 남으면, **C**(확장)는 2단계 이후다. 모델 번호(M1\~M7)는 SDD와 같다.

### 3.1 측정 (FR-MEA)

| ID | 요구사항 | 우선순위 | 관련 모델·오픈소스 |
| --- | --- | --- | --- |
| FR-MEA-01 | 시스템은 소나 에코그램을 수신해 수심 구간별 어군 분포를 계산해야 한다 | M | M4, echopype |
| FR-MEA-02 | 시스템은 에코그램에서 어군 활동량을 계산해야 한다 | M | M4 |
| FR-MEA-03 | 해커톤에서는 수온·층간 수온 차·DO에 따라 변하는 합성 에코그램을 만들어야 한다 | M | 개체 기반 시뮬레이터 (자체 개발) |
| FR-MEA-04 | 시스템은 수중 카메라 프레임마다 영상 품질 점수(0\~1)를 계산해야 한다 | M | M1, OpenCV |
| FR-MEA-05 | 시스템은 품질이 낮은 프레임에 수중 영상 개선을 적용해야 한다 | S | M2, OpenCV CLAHE → FUnIE-GAN |
| FR-MEA-06 | 시스템은 영상에서 물고기를 탐지하고 개체 ID를 추적해야 한다 | M | M3, RF-DETR 또는 Community Fish Detector + trackers(ByteTrack) |
| FR-MEA-07 | 시스템은 표층·중층 수온과 DO를 수집해야 한다 | M | 해커톤은 시뮬레이터 생성값 |
| FR-MEA-08 | 시스템은 수과원 수온·특보 자료를 가져와야 한다 | S | 수과원 어장정보시스템 (연동 방식 확인 필요) |
| FR-MEA-09 | 시스템은 실제 Ping360 소나에서 데이터를 받을 수 있어야 한다 | C | bluerobotics-ping (brping) |
| FR-MEA-10 | 시스템은 카메라 추적 결과에서 개체가 그물·바닥에 몸을 비비는 횟수(시간당)를 세야 한다. 영상 품질 0.6 이상 구간만 쓴다 | S | M3 추적 결과 + 비비기 판정 (자체 개발) |

## 4. 비기능 요구사항

가장 중요한 비기능 요구는 **거짓 경보 억제**와 **설명 가능성**이다. 어민이 거짓 경보를 몇 번 받으면 서비스를 믿지 않게 되고, 재산 결정에는 근거가 필요하다. 수치 목표는 현장 실증 전 가설값이며 3단계에서 재설정한다.

| ID | 분류 | 요구사항 | 목표값 |
| --- | --- | --- | --- |
| NFR-PER-01 | 성능 | 엣지에서 카메라 탐지·추적 처리 속도 | 5 FPS 이상 (Jetson 급) |
| NFR-PER-02 | 성능 | 센서 수집부터 스트레스 지수 갱신까지 지연 | 5분 이내 |
| NFR-PER-03 | 성능 | 경보 단계 상승부터 알림 발송까지 지연 | 1분 이내 |
| NFR-PER-04 | 성능 | 대시보드 초기 화면 로딩 | 3초 이내 |
| NFR-REL-01 | 신뢰성 | 영상 품질이 낮을 때 탐지 수 감소를 이상으로 판단하지 않음 (품질 게이트) | 합성 탁도 시나리오에서 거짓 경보 0건 |

| NFR-USE-02 | 사용성 | 어민 화면은 글자 크기를 크게 하고 핵심 행동 버튼은 1단계로 접근 | — |
| NFR-SEC-01 | 보안 | 어가 경영 정보(마릿수, 보험, 손익)는 해당 어가와 권한 있는 공무원만 열람 | 역할 기반 접근 제어 |

### 5.5 통신 인터페이스

- 현장 → 서버: LTE, **영상 원본이 아닌 지표만** 전송 (MQTT 또는 HTTPS).

- 모든 외부 통신은 TLS를 쓴다.

## 6. 데이터 요구사항, MVP 범위, 유스케이스

해커톤 MVP는 \*\*조피볼락, 센티넬 가두리 1개, 여름 복합재해 시나리오, ✅ 지표 2개(수직 분포·활동량)\*\*에 집중한다. 가장 큰 데이터 리스크는 조피볼락 수중 영상이다.

### 6.1 데이터 요구사항

| --- | --- | --- | --- | --- |

| DR-02 | 소나 에코그램 | M4 | 합성 데이터 (해커톤), 연구기관 협조 | 합성으로 대신 |

### 6.2 해커톤 MVP 범위

- [ ] 합성 소나 데이터 생성기 (수온·층간 수온 차·DO에 따라 수직 분포와 활동량 변화)

- [ ] 품질 가중 센서 융합
- [ ] M5 밤낮 분리 비지도 스트레스 지수 (PyOD Isolation Forest)

- [ ] 원인별 대응 + 손익 계산기 (긴급방류 요건 자동 확인, 질병 계열 공통 1차 조치)

## 7. 검증 기준, 리스크, 추적성

해커톤 검증은 합성·공개 데이터 기준이며, 실제 효과는 3단계 현장 실증에서만 확인할 수 있다. 최대 리스크는 **국내 조피볼락 가두리에서 행동 기반 스트레스 측정이 미검증**이라는 점이다.

### 7.1 검증 기준 (해커톤)

| ID | 검증 항목 | 방법 | 통과 기준 |
| --- | --- | --- | --- |
| VC-01 | 탁도 구간별 지표 안정성 | 카메라 단독 vs 소나 융합 비교 | 탁도 높음 구간에서 융합 지표 변동이 더 작음 |
| VC-02 | 스트레스 지수 이상 구간 탐지 | 합성 시나리오 정답 구간 대비 | 재현율 0.8 이상 (목표) |
| VC-03 | 원인 추정 정확도 | 시나리오별 정답 원인 대비 | 4개 시나리오 모두 정답 원인이 1순위 |
| VC-04 | 경고 선행 시간 | 28℃ 주의보 시점 대비 '주의' 발령 시점 | 선행 시간 양수 (시뮬레이션) |
| VC-05 | 탁도 상승 거짓 경보 | UC-03 시나리오 | 거짓 경보 0건 |
| VC-06 | 알림 이해도 | 간단한 사용자 테스트 | 이해율 80% 이상 |
| VC-07 | 탐지 모델 조피볼락 적용성 | 조피볼락 이미지 10\~20장에 Community Fish Detector 실행 | 놓친 개체·오탐 수 기록 (기준값 없음, 보고용) |
| VC-08 | 질병 계열 대응 안전성 | 질병·기생충 의심 시나리오의 추천·알림 전수 확인 | 약품명·투약량 0건, 1차 조치와 진단 요청 생성 |

### 7.2 리스크

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 현장에서 행동 전조가 잡히지 않음 | 핵심 가치 상실 | ✅ 지표 2개 중심, 2·3단계 실증 |
| 실측 영상·소나 데이터 부족 | 모델 성능 불확실 | 합성 데이터, 소량 라벨, 연구기관 협력 |

| FUnIE-GAN 라이선스 불명확 | 상용화 제약 | 해커톤은 OpenCV CLAHE 우선, 라이선스 확인 후 도입 |
| 기존 플랫폼과 중복 | 차별성 약화 | 행동 기반 진단 + 원인 추정 + 결정 지원 유지, 연동 검토 |
